# S9 spikes — scheduler ground truths

Machine/toolchain per S0.md (Scala Native 0.5.12, macOS arm64). Measured 2026-11-09.

## A. §6.4 raw trigger probability machine-guns a HEALTHY log — floor added

Plan §6.4 triggers alerts per tick with probability
`p = triggerBase + (1 - triggerBase) · S` with `triggerBase = 0.10` (§4.1).
At the §7.3 row-1 steady state for a perfectly healthy 10-info/min log
(`S ≈ 0.06`), `p = 0.154` per tick. The lottery is drawn **every tick** (20 Hz),
so expected alert starts ≈ `20 · 0.154 ≈ 3.1/s` asked; the §7.2 guard
(`minIntervalMs=150`, burst 3/2000ms) PACES them to ≈ 1.5/s sustained — but a
calm log would still emit an ~180 ms saw blip every ~700 ms forever. That is
not the "calm consonant bed, no alerts" perception §7.3 row 1 demands.

**Decision:** the scheduler skips the draw entirely below a severity floor,
`SchedulerOptions.alertMinSeverity` (default `Scheduler.AlertMinSeverityDefault
= 0.15`). Rationale for 0.15:

- info-only (§7.3 row 1): S_ss = 0.0050·8/ln2 ≈ 0.058 < 0.15 → silent. ✔
- 1 warn/min (row 2): S_ss ≈ 0.058 < 0.15 → silent. ✔
- 1 error/min (row 5): S_ss ≈ 0.192 > 0.15 → occasional alerts kept. ✔
- 6 warn/min (row 3): S_ss ≈ 0.346 → alerts on drift allowed (guard paces). ✔

The floor is the ONE deviation from the plan formula in this slice; it is a
constructor default, overridable (`SchedulerOptions(alertMinSeverity = 0.0)`
restores the raw §6.4 behavior, exercised in SchedulerSpec's triggerBase test).
S14 tuning may move or remove it with §7.3 as the table.

## B. mix-tick event dedup (goldens stay readable)

`applyParams` is called EVERY tick (engine heartbeat — S10/S15 engines may use
it as a liveness/param-refresh hook). The `--print-events` `kind=mix-tick`
event fires only when a quantized key (severity+4 gains rounded to 1e-3)
CHANGES; a 20 Hz emission of near-identical decay values would drown goldens
(800 lines per 40 s of storm). Quantization is `Scheduler.mixKey`; the final
stop-fold also emits when its key differs (so the last engine-visible mix
state is always visible in the stream).

## C. Tick cadence is deadline-driven, not sleep-driven

`nextDeadline += tickMs` regardless of overrun; the sleep seam sleeps
`max(0, nextDeadline - now)`. A slow tick is compensated (no drift over
hours); an overrun burst never queues (bed-grid catch-up mirrors this). Tests
drive the same code through `runSync`/`tickOnce`/`awaitDeadline` with a
FakeClock whose time moves ONLY through the sleep callback → fake time lands
exactly on `k·tickMs`; goldens reproducible.

## D. Reader→scheduler queueing

Two-buffer MPSC under one monitor (`submit` appends; `drain` folds+clears once
per tick). Chosen over `ConcurrentLinkedQueue` for zero-dep, visibly bounded
allocation and negligible contention at 20 Hz consumer rate. `Severity.addEvent`
is called ONLY on the scheduler thread (S3 single-owner contract holds —
verified: `addEvent` has no other call site outside tests).

## E. Manual headless observation (linked binary, §8)

`scripts/gen`-free eyeball run, mixed log (info+warn+error) piped through
`--backend null --print-events` — see the S9 commit message for the verbatim
observations (bed notes on the 600 ms grid, warn drift crossing layers=1,
error storm pinning severity=1.0 with guard-paced alert-starts, single
engine-stop with fadeMs=400, stdout byte-identical).
