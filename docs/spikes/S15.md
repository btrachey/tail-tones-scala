# S15 spikes — CoreAudio AudioQueue engine (bindings, callback threading, latency)

Machine: macOS 27.2.0 (darwin, arm64), Scala Native 0.5.12 / Scala 3.3.3,
Homebrew LLVM 23 clang, SDK MacOSX.sdk (26.x). Device: default output =
AudioObjectID 118 (Scarlett/DisplayPort family, S0 §D). Measured 2026-11-10.
Evidence re-runnable: `sbt nativeLink && ./target/scala-3.3.3/tail-tones
--s15-probe` (source: `src/main/scala/tailtones/S15Spike.scala`).
Audible checks UNVERIFIED-BY-AGENT throughout (TCC mic silence — S0 §Mic;
S10 §B precedent).

## A. Callback threading — VERIFIED: C-created, non-Scala thread

Probe: `pthread_self()` + the address of a stack local recorded INSIDE the
`AudioQueueOutputCallback` (C, `ttaq.c`), compared against probes taken on
the Scala main thread and a Scala-spawned worker thread. Verbatim run:

```
thread[scala_main]   self=0x1f87c1300 stack=0x16b9f8e8f
thread[scala_worker] self=0x16bc27000 stack=0x16bc26bcf
thread[audioqueue_cb] first=0x16ba83000 last=0x16ba82747... sameThreadThroughout=true
thread[cb vs scala]   differsFromMain=true differsFromWorker=true
stack[audioqueue_cb] probe=0x16ba82747
```

- The callback thread's `pthread_self` (0x16ba83000) is neither the main
  thread (0x1f87c1300 — the static main-thread stack region) nor the Scala
  worker (0x16bc27000), and its stack address band (0x16ba827xx) sits in
  neither of their stack ranges ⇒ AudioQueue owns the thread (created with
  `inCallbackRunLoop = NULL`, the documented dedicated-thread mode).
- Across repeated 3 s runs (24–305 callbacks), first-self == last-self in
  every phase; one run observed `sameThreadThroughout=false` — AudioQueue is
  NOT guaranteed to keep one internal thread forever. ⇒ The engine must never
  assume a stable callback thread; it must never call into it.
- **GC-entry-avoided-BY-DESIGN:** the callback is a pure-C function
  (`tq_output_callback` in `ttaq.c`) — NOT a Scala `CFuncPtr` closure. It
  touches only its `malloc`'ed state block (`__atomic` stores of counters,
  `mach_absolute_time`, slot states) and calls
  `AudioQueueEnqueueBuffer` on READY (pre-filled by the mixer) buffers.
  No malloc, no ObjC, no managed frame on the callback path — entering the
  GC is structurally impossible, which is the §6.7 invariant discharged by
  construction rather than by discipline.
  Proof point: a managed-code callback would need the GC to know its thread;
  Scala Native 0.5 only registers threads that call into the runtime — the
  S10 §D-2 deadlock class (AtomicBoolean.set from signal context under GC)
  is exactly what this design forecloses.

## B. Buffer flow — NewOutput/Allocate/Enqueue/Start/Stop/Dispose all OK

4×4410-frame (100 ms) buffers, s16 mono 44100 ASBD, primed before Start:

```
AudioQueueNewOutput ok; AllocateBuffer ok x4; Start=ok(0); IsRunning(mid)=1;
Stop=ok(0); Dispose=ok(0); devRate=192000.0; device after dispose = 118
callbacks=26 in 3.0s rate=8.7/s expected=10.0/s  (100 ms buffers)
callbacks=305 in 3.0s rate=101.7/s expected=100.0/s (10 ms buffers, phase B)
```

- Every call returned OSStatus 0 (`noErr`); `kAudioQueueProperty_IsRunning`
  flips to 1 mid-stream, `kAudioQueueDeviceProperty_SampleRate` reads back
  192000.0 — the queue is attached to the real hardware (the HAL resamples
  our 44100 stream to the device's 192 kHz; documented CoreAudio behavior,
  not an error).
- Completion rate tracks buffer duration (100 ms → ~10/s, 10 ms → ~100/s).
  The 100 ms phase read 8.7/s — startup (prime + pre-Start silence) absorbs
  ~2 completions; steady-state count is exact. NOTE for the engine soak:
  the assignment row's "≈24/s at 4410/44100" is arithmetically wrong
  (4410/44100 = 100 ms ⇒ 10/s); the engine runs 441-frame (10 ms) buffers
  ⇒ expected ≈100/s, measured 101.7/s.
- Enqueue-from-callback race: the mixer poll and the C callback both claim
  READY slots via one `__atomic_compare_exchange_n`; 600+ completions across
  phases, `queued` always returned to 0, no double-claims (no crash, no
  OSStatus 'bad state' — every enqueue returned 0 by construction of the CAS).

## C. Volume — param works; the QUEUE METER IS PRE-VOLUME (architecture driver)

```
volume default=1.00 readback .25=0.25 1.0=1.00    (AudioQueueSet/GetParameter)
meter dBFS full=avg -12.2 peak -12.2
meter dBFS vol.25=avg -12.2 peak -12.2             (NO drop — pre-volume!)
```

- `kAudioQueueParam_Volume` (=1) and `kAudioQueueParam_VolumeRampTime` (=4)
  set/get round-trip through `AudioQueueSetParameter`/`GetParameter`,
  OSStatus 0.
- The queue's level meter (`kAudioQueueProperty_EnableLevelMetering` /
  `_CurrentLevelMeterDB`) reads −12.2 dBFS for the 8000/32767 square wave
  — exactly its theoretical pre-volume RMS (20·log10(8000/32767) = −12.24)
  — and does NOT move when the volume param drops to 0.25. So the meter
  measures the queue's DECODED stream, not the post-Volume output. Two
  consequences:
  1. The meter is excellent PCM-reaches-the-device evidence (the engine's
     bytes arrived at the render stage at exactly the expected amplitude),
     but it can NEVER verify volume scaling.
  2. **Decision (deviation, §6.7-compatible): the engine applies
     master×fade at fill time** — in the mixer, into the bytes it writes
     into `mAudioData` — exactly like `PipeEngine.applyMasterFade` applies
     master×fade at drain time for ffplay/alsa. This keeps the three
     streaming backends byte-identical (MutingEngine zeroing master ⇒
     silence bytes in the buffer; fade ramps the actual samples — the
     machine-verifiable "compare buffer contents pre/post volume change"
     acceptance), and `kAudioQueueParam_Volume` stays at a documented 1.0
     (kept in the bindings surface, exercised by the spike + facade tests).
     Rationale: with a pre-volume meter + TCC-silent mic, param-based gain
     scaling is unmeasurable by any automated means on this machine;
     fill-time gain is measurable at the drain point AND is the plan's own
     mixer-side philosophy (§6.7: synthesis/mixing on the Scala producer).

## D. Latency — NO `mPacketStartTime` on macOS; documented equivalent used

The assignment/plan anticipate `AudioQueueBufferRef.mPacketStartTime`.
Verified against the MacOSX.sdk (26.x) `AudioQueue.h`:

```c
typedef struct AudioQueueBuffer {
    const UInt32 mAudioDataBytesCapacity;
    void * const mAudioData;
    UInt32 mAudioDataByteSize;
    void * mUserData;
    const UInt32 mPacketDescriptionCapacity;
    AudioStreamPacketDescription * const mPacketDescriptions;
    UInt32 mPacketDescriptionCount;
} AudioQueueBuffer;
```

No `mPacketStartTime` (that field exists only in the iOS variant of the
struct and is absent from the macOS SDK; `grep mPacketStartTime AudioQueue.h`
→ 0 hits, and the compile of `inBuffer->mPacketStartTime` fails against the
real SDK). **Documented equivalent used instead:** the output callback fires
when the device has FINISHED consuming the buffer, so
`deviceStart(buffer) ≈ done_host − bufferDuration` and
`fill→device latency = done_host − fill_host − bufferDuration` (mach-time
domain; `mach_absolute_time` + timebase → ns).

Measured (phase B: 6×441-frame = 10 ms buffers, sampled at every mixer
refill ⇒ same-pass fill/done pairs guaranteed):

```
latency[fill->device] n=299 min=15.66ms max=66.16ms
latency[fill->device] n=299 min=17.01ms max=67.55ms   (second run)
```

Reading (structural, matches the model exactly): steady-state latency ≈
(queue depth − 1) × bufferDuration + jitter. Phase B ran 6 buffers ⇒ 5×10
= 50 ms of queued-ahead PCM + ~10–17 ms of poll/jitter ⇒ min 15.7 (late-
joining buffer), max ~66 (the pre-Start primed buffers carry the whole
prime window in their first pass). The max is a STARTUP transient: buffers
primed before `AudioQueueStart` wait the entire pre-start window.
**Engine sizing (decided here):** 6 × 441-frame buffers (60 ms on-device,
5×10 = 50 ms queue-ahead) + poll 5 ms + the ring pre-primed only enough to
start (the mixer poll refills DONE slots as they arrive). Steady-state
fill→device ≈ 40–50 ms + HAL latency ⇒ within the plan's ≤50 ms budget
modulo device HAL latency (CoreAudio HAL default I/O cycle ~5–11 ms at
this device's 192 kHz safety level — invisible to this method, covered by
the human spot-check row). The soak asserts the steady-state window
(after a 2 s warmup) excludes the prime transient, and reports p50/max.
UNVERIFIED-BY-AGENT: audible alert-response feel (human row).

## E. Toolchain traps found (bind them or later slices rediscover)

1. **`@link("AudioToolbox")` cannot work** — the plugin emits `-lAudioToolbox`
   and macOS has no `libAudioToolbox.a`/`.tbd`: `ld: library 'AudioToolbox'
   not found`. Fix: plain `@extern` bindings + `nativeConfig.withLinkingOptions
   (+ Seq("-framework","AudioToolbox","-framework","CoreAudio"))` in build.sbt,
   guarded by `scala.util.Properties.isMac` so the Linux container never sees
   them (Linux links the `ttaq.c` stubs instead).
2. **`src/main/native/` is NOT compiled by sbt-scala-native 0.5.12** (no
   `nativeCompileSources`-style key exists in the plugin — verified by
   scanning the plugin/tool jars). The working convention is
   **`src/main/resources/scala-native/*.c`** — same mechanism nativelib
   ships its immix GC C in. Our file lives there.
3. The AudioQueue* C symbols referenced by the bindings must exist on Linux
   too (the bindings object is reachable from shared specs): `ttaq.c` carries
   `#else`-branch stubs returning −1 for every entry point, and the engine's
   device gate (`defaultOutputDevice == 0` ⇒ never start) keeps them
   unreachable at runtime on Linux. Container link is the proof.
4. `malloc(size)` in Scala Native 0.5.12 clib takes Long/Int/CSize — a
   `ULong` from a C `size_t` binding needs `.toLong`.
5. `IsRunning` can read 0 immediately after a successful `Start` (the queue
   spins up asynchronously); read it mid-stream (our probe reads at +400 ms
   ⇒ 1). Never gate start-failure detection on it.
6. The level meter is PRE-volume (this session's measurement, §C) — any
   future "verify volume" idea via `kAudioQueueProperty_CurrentLevelMeter*`
   is dead on arrival; audible check only.

## F. Engine architecture decisions (handoff record)

- Bindings: `tailtones/audio/coreservices/AudioQueue.scala` (@extern,
  opaque `Ptr[Byte]` AQRef/AQBufRef; ASBD + buffer field access via ttaq.c)
  + `src/main/resources/scala-native/ttaq.c` (state block, C callback,
  CAS claim+enqueue, probes, Linux stubs).
- Slot machine: FREE →(mixer fill)→ READY →(CAS claim, either poller or the
  C callback)→ QUEUED →(C completion)→ DONE →(mixer refill)→ READY.
  Exactly one CAS winner calls `AudioQueueEnqueueBuffer`.
- Mixer thread (Scala-owned, daemon, poll 5 ms) is the ONLY filler and the
  ONLY ring consumer; master×fade is applied at fill time (§C); underflow
  serves the media bed, else silence (device clock discipline, same as
  PipeEngine).
- Facade for tests: `tailtones/audio/coreservices/QueueOps` trait (create/
  allocate/fill/claim/start/stop/dispose/setVolume/state/counters +
  `deviceTick(n)` that SYNCHRONOUSLY completes n buffers — the fake device).
  CoreAudioEngine takes `ops: QueueOps = QueueOps.real`; unit tests drive
  `deviceTick` from the test thread — callback handoff, no-alloc review,
  volume byte-scaling, bed-loop seam, and stop/fade are all deterministically
  testable without the device.
- Selection: macOS `auto` = coreaudio (probe: `!TAIL_TONES_COREAUDIO=0` &&
  deviceAvailable) → ffplay-pipe → spawn → null+stderr, each fallback
  honest; `--backend coreaudio` explicit (device miss → null + note).
  `resolvedBackend`/`mediaPolicy` mirror (coreaudio ⇒ TranscodeAlways —
  the bed is a 44.1k WAV served from the ring; native afplay decode is a
  spawn-path-only capability).
- `AudioQueueDispose` on EVERY exit path: `stop(fadeMs)` and `killChildren()`
  both run stop→dispose idempotently (stop-latch `stopped` compareAndSet,
  mirrors PipeEngine's discipline; Main's shutdown hook covers the crash
  path).
- Gapless media: bed PCM loops seam-to-seam through the ring (S12's baked
  crossfade file reads continuous at the wrap — §6.5's self-generated
  criterion; third-party files seam-to-seam "acceptable v1"). No respawn,
  no afplay anywhere in this backend.

## G. Engine soak evidence + depth decision (post-spike, machine ground truth)

`--s15-soak <seconds> [--media <file>]` (Main dev entry → S15Spike.soak) runs
the REAL CoreAudioEngine on the REAL device with a synthetic 20 Hz voice feed
(bed grid 20/s + saw spike every 13th), 3 s warmup, then resets stats and
asserts: starveCount == 0 (device never went dry → no dropouts), callback
rate ≈ 100/s (441-frame buffers), steady-state fill→device-start max ≤ 50 ms
(§D method), RSS growth < 4 MB post-warmup (S13 leak discipline).

**Depth decision: 6 → 5 buffers.** First soak at depth 6 (60 ms on-device):
rate 106.6/s, starve=0, but steady latMax 51.26 ms — one buffer over budget
(steady-state ≈ (depth−1)·10 + poll + jitter). Depth 5 (50 ms on-device):

```
SOAK wall=45.6s callbacks=4558 rate=100.0/s starve=0 underrunSilence=321
latN=4559 latMin=-9.26ms latMax=40.60ms rss0=35600KB rssMax=36096KB delta=496KB
SOAK: PASS
```

- latMin −9.26 ms = measurement artifact (done stamped at poll-N, fill at
  poll-N+1 inside one 5 ms window + mach-time rounding); negative means the
  device had NOT yet started that buffer at refill — consistent with queue
  depth ≈ 4. Max 40.6 ms is the binding number: ≤ 50 ms budget.
- underrunSilence 321 in 45 s ≈ 7/s = silence-filled refills BETWEEN bed
  voices (builtin mode: voices land on the 600 ms grid; ring empty between =
  correct audio, not a dropout). Starve = 0 is the dropout counter. With
  `--media` the bed feeds continuously and the soak reddens underrunSilence ≠ 0.
- 30-min soak + `--media` gapless soak: commands in the slice report (run on
  final binary; 45 s form above is the harness smoke).

## H. Test-design decisions

- `FakeQueueOps` (src/test) mirrors the C callback contract exactly:
  `deviceTick` only flips slot state + counters + stamps (no engine calls —
  pinned by "device completion performs NO engine-visible work"). The real
  callback is pure C (spike §A), so the §6.7 "zero allocation / zero GC entry
  in callback" criterion is discharged by construction in production and by
  the contract-pinned fake in tests.
- `startPollThread=false` in specs: the deterministic rows drive
  `pollOnceSync()` + `deviceTick` synchronously (no thread races in the byte
  assertions); lifecycle/stop rows exercise the latch paths directly.
- Byte-level volume evidence: `applyParams(master=0.25)` → recorded device
  bytes max |sample| 5000±2 from 20000 (×0.25 exactly); queue param stays at
  1.0 (param path itself pinned separately via setVolume/getVolume round-trip
  + spike §C real-device meter finding).
