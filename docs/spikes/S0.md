Read this table carefully — three tiers, plan §2 said two:

1. **Throws at `Pattern.compile`** (better than plan's "fails at runtime"): all lookarounds, possessive, atomic, `\G \R \Z \h \e`, `\p{java…}`. A shipped bad pattern dies loudly at startup in tests, not silently at match time.
2. **Compiles but SILENTLY NEVER MATCHES** (more dangerous than throwing): `\v` (compiles, matches nothing), `\0100` octal (compiles, does **not** match `@` — RE2 has no octal; it parsed as something else), char-class intersection/subtraction `[a-z&&[^aeiou]]` (compiles, does **not** match `b` — RE2 supports `&&` but SN's translator doesn't deliver it). **Never use `\v`, octal escapes, or `&&`/`--` inside classes; tests must assert the POSITIVE (that the pattern matches its example input), not just that it compiles.**
3. **Safe shapes for S4/S5**: alternation + `\b` + classes + `(?i)` + `\x1b` + `\p{Alpha}` all compile **and** match. `\xFF` (two-char hex) is accepted here.

**`Pattern.matches()` is whole-string anchored** — level-detection must use `matcher.find()` (the `matches=false` rows above are the same patterns that `find=true`). This bit S0's own test; S4's keyword parser must default to `find()`.

## D. afplayStartMs — cold ≈ 1430 ms, warm ≈ 400–900 ms; plan's 120 ms is too small

Method: native binary spawns `/usr/bin/afplay` via `os.proc(...).call()` (blocks to child exit) on (a) `/usr/bin/true`, (b) a **0 ms** WAV (1 s16le frame) → wall ≈ spawn + CoreAudio wake + teardown, (c) a 2000 ms silent WAV. Verbatim:

```
== afplay startup latency probe ==
/usr/bin/true spawn wall (ms): 2, 2, 3, 3, 5 (median 3)
afplay 0ms-file wall (ms): 1422, 1422, 1426, 1430, 1434 (median 1426)
afplay wall times (ms) for 2000ms file: 2935, 3432, 3433, 3433, 3437
afplayStartMs estimate (median wall - 2000ms) = 1433
min=2935 max=3437
```

- Pure spawn overhead ≈ 3 ms — the ~1.4 s is **afplay/CoreAudio fixed cost** (device wake + teardown), not os-lib.
- 2 s file: wall ≈ 2.93–3.45 s → per-play overhead ≈ 0.9–1.4 s (bimodal: ~2.93 outliers vs ~3.43 mode).
- Second probe (bash, `time`): with audio already playing on the device ("warm", one 8 s playback in flight), 0 ms ticks cost **405–911 ms** instead of ~1430 ms cold.
- **Spawn→audible could NOT be measured on this machine**: mic capture returns pure digital silence (Terminal lacks TCC mic permission; every capturable input device — built-in mic, Teams driver, iContact driver — records max-amplitude 0) and default output routes to the Scarlett 2i2/DisplayPort with nobody able to hear it. No `afplay` flag exposes playback-start timing (`-d` prints format only). `[INFERENCE]` audible onset ≈ the warm fixed cost, since the 0 ms wall is dominated by open-device→close-device.

**Decision/impact for S12 (ping-pong pre-spawn):** keep the offset a config tunable, but plan default 120 ms is ~10× too small for a **cold** device. During an actively playing bed (the ping-pong case) use ≈ **900 ms**; S12 should measure in-context (`afinfo` duration vs. child wall time of successive overlaps) rather than trusting any pre-baked constant. Musically acceptable per plan §6.6 tolerance (±1 tick).

## E. ffplay-pipe — VIABLE (promote; replaces spawn+alsa-pipe candidate)

ffplay 9.0.2. The original rejection was **ffplay rejecting `-ac`/`-channels` as input options** ("Failed to set value '1' for option 'ac': Option not found") — not a pipe/PTY problem. Working invocation:

```
ffplay -f s16le -ar 44100 -i pipe:0 -nodisp -autoexit
```

Evidence (all on this machine, 2026-11-09):
- Feeding a 2 s mono s16le PCM file on **plain stdin (no PTY needed)**: input detected `Stream #0:0: Audio: pcm_s16le, 44100 Hz, mono, s16, 705 kb/s`, clock advanced through `M-A:` frames, **exit 0**.
- `-ac 1` and `-channels 1` before `-i`: **both rejected** ("Option not found") — omit them; the s16le raw demuxer **defaults to mono** (confirmed: stereo PCM still reported mono without channel opts; `-ac 2` pre-`-i` exits 1). Mono-only matches the plan's `PcmSink` (s16 mono) — fine for v1; stereo would need a different option form (post-`-i` output-side, unprobed).
- **One persistent child, multiple tones:** `cat tone2s; sleep 0.2; cat tone2s; sleep 0.2; cat tone2s` → single ffplay handled all 3, wall 6.95 s vs 6.0 s audio (≈0.95 s pipeline lag, no stalls) — exactly the mixer-fed-stream use case.
- Drain-on-close: 2 s file → exit 2.91 s after stdin close (3 samples) — ffplay buffers ~0.9 s and exits promptly at EOF (`-autoexit` works with EOF on a pipe).
- Real-audio caveat: same machine-wide constraint as D — cannot prove "sound came out" via mic (TCC). Verdict rests on successful decode, monotonic clock advance, clean exit, and known-good SDL output path. `[INFERENCE]` audible.

**Verdict: VIABLE.** Per plan §6.1 this *replaces* both `spawn` and `alsa-pipe` candidates: one `ffplay-pipe` backend, both OSes, feeding the shared `PcmSink` ring. S10/S11 decide; the exact option order above is the one that works here (Linux untested here — S11 must re-probe, `-nodisp` and SDL audio are portable).

## F. sbt-scala-native plugin: 0.5.1 → 0.5.12 — BUMPED (mandatory, not optional)

0.5.1 **fails to link** on this repo as configured:

```
java.lang.AssertionError: assertion failed: Can't read binary-incompatible version of NIR from
'.../nativelib_native0.5_3/0.5.12/nativelib_native0.5_3-0.5.12.jar:/java/lang/Object.nir'
(expected compat=6, got 6; expected revision=10, got 11)
```

Root cause: the allowlisted **munit 1.3.6 (`munit_native0.5_3`) transitively pulls the 0.5.12 nativelib/scalalib jars**; the 0.5.1 linker can't read their NIR (revision 11 vs 10). So with the plan's pinned test dep, the toolchain MUST be ≥0.5.12. After the bump: `sbt test` green (4/4) and `sbt nativeLink` green — acceptance stayed green, bump stands. clang LLVM 23 is fine with 0.5.12. `project/plugins.sbt` now reads `0.5.12`.
