# S12 spikes — media mode (bed pipeline, ping-pong loop, transcodes, temp lifecycle)

Machine: macOS (darwin 27.2.0, arm64), Scala Native 0.5.12 / Scala 3.3.3.
Measured 2026-11-10. Container ground truth: devcontainer (Debian trixie,
mpg123 1.32.10, ffmpeg 7.1.x — results quoted inline below from `verify.sh`
step 7 + full `sbt test`).

## A. Ping-pong gap math (plan §6.6) — PASS (formula level)

`afplayStartMs` = 1450 ms (S0 spike D, reused; S10 measured 1.44 s cold
in-context — NOT re-measured here).

- `MediaBed.pingPongDelayMs(durMs, lead)` = `max(0, durMs − 1450)` — the plan
  formula, pinned verbatim in `MediaBedSpec` ("gap-formula acceptance").
- `MediaBed.loopSpawnSpacingMs(content, lead, floor, cap)` caps the overlap at
  300 ms (deviation, see §D-2) and floors at 50 ms (anti-spin):
  `spacing = max(50, min(content, max(content/2, content − min(lead, 300))))`.
- Gap per iteration = `max(0, spacing − content)`. For every content in
  {500, 1000, 2500, 4000, 10000, 30000} ms: **gap = 0 ms** (spacing ≤ content,
  overlap ∈ [0, 300] ms) — `MediaBedSpec` "overlap capped, floor half-content,
  anti-spin minimum".
- Real proof at the binary level (`MediaE2eSpec` ping-pong): wav bed 1500 ms +
  fake afplay that sleeps 3 s. Plain respawn-after-exit CANNOT have two live
  children; `pgrep -P <parent>` saw **≥2 overlapping children** and the marker
  file ≥2 spawns → ping-pong pre-spawn confirmed end-to-end.

UNVERIFIED-BY-AGENT: human-ears gapless quality (TCC silences audio in this
environment, S0/S10 precedent). The ≤30 ms claim is formula + overlap-
observation level only. HUMAN LISTENING REQUIRED: `--mode media --backend
spawn` with a real bed; judge whether the 300 ms overlap sounds like a flam
(per-genre; see §F).

- **Real mpg123 + ffmpeg on Linux** (container, verify.sh step 7):

  `--backend alsa-pipe --mode media --media sine-440-1s.mp3` → exit 0

## D. Decisions (deviations from plan draft, with rationale)

1. **Crossfade baked at transcode time, not in `fillBedLoop`.** Plan §6.5 says
   "5 ms linear crossfade on the seam for SELF-generated loops". Baking into
   the transcoded WAV (`MediaBed.applyLoopCrossfade`, w(i) = (i+1)/(xf+1),
   tail[i] ← tail·(1−w) + head[i]·w) means BOTH consumers of the same file —
   PipeEngine ring fill AND afplay ping-pong respawn — get the seam-treated
   audio with zero runtime cost and no double-fade. `setBedLoop` therefore
   must NOT crossfade `selfGenerated` buffers again (doc'd at both sites).
   Third-party files: NO crossfade anywhere — plan's "seam-to-seam acceptable
   v1". **Self-generated = transcoded output only.** A synth bed from the
   builtin path never enters media mode; a user WAV is third-party even if
   they generated it themselves — provenance is the resolver, not the bytes.
2. **300 ms overlap cap.** Pure plan formula (spawn at `durMs − 1450`) makes
   N+1's AUDIO start 1450 ms before N's audio ends — for a 2 s bed that is
   >70 % overlap: two identical beds phasing/flamming, far worse than a short
   gap. Cap = 300 ms overlap keeps "gap = 0" (the acceptance bound ≤30 ms is
   about the GAP, and the gap is 0 by construction) without the flam. Floor
   content/2 keeps ≥50 % of content unique per iteration; 50 ms anti-spin.
3. **Loop restart at frame 0** (all beds). The baked blend makes last→0
   continuity ≈ head's own 5 ms evolution; an xf-offset restart would skip
   real content and double-play nothing gained. `fillBedLoop` pins
   `bedPos = 0` at wrap; `MediaBedSpec` seam test measures |last − first|
   collapsing from 8001 → <800 with flat head material.
4. **Transcode cache by (canonical path, size, mtime)** — Main's startup
   validation and the engine's `setBedLoop` share ONE transcode ("one-time
   startup transcode" plan §6.5). Release on stop; `Main` finally-path
   `cleanupAll` backstops engines that never got `stop`; `deleteOnExit`
   backstops SIGKILL (S0 spike C: javalib atexit runs).
5. **No own shutdown hook** → S10 §D-3 hook-ordering trap cannot recur
   (everything is cooperative stop + deleteOnExit).
6. **`killChildren` joins the media loop thread BEFORE kill sweeps.**
   Reproduced bug: TERM during ping-pong orphaned **7** `sleep 30` fake
   children — `registry.killAll` snapshots, and the loop registered a fresh
   child after the last sweep. Fix: `loopRunning=false` + interrupt +
   `joinQuietly(t, 300)` before the sweeps (`SpawnEngine.killChildren`).
   Re-verified: 6 children alive at TERM → 0 strays after, exit 0.

## E. Temp-file lifecycle — PASS (with one infra finding)

`tail-tones-media-*` dirs in `os.temp.dir(deleteOnExit=true)`; released on
`stop()` AFTER loop-thread join + child kill (never delete a WAV an afplay
child may still read); `cleanupAll` on Main's finally; failed transcodes
remove their dir before returning Left (container verifies 0 leaked dirs
after exit-2 runs; host test diffs tmp listings — other suites legitimately
hold live dirs in the shared binary).

**FINDING: `deleteOnExit` is NOT a reliable backstop in-container.** The
container's first full-suite run left 9 `tail-tones-media-*` dirs and the
test binary's stderr showed WHY:
`Exception in thread "subprocess-shutdown-hook" java.io.IOException: Unable
to posix_spawn process [res=2, errno=2]` — javalib's deleteOnExit machinery
spawns `rm -rf` children at exit (javalib `UnixProcess` in a shutdown hook),
and when the sbt JVM tears down the spawn itself fails (race with the dying
JVM's env/PATH or fork exhaustion under 500 tests). Consequence: the ONLY
reliable cleanup is explicit cooperative release — which is exactly why
`clearCacheForTesting` now calls `cleanupAll()` (was a bare `cache.clear()`
that LEAKED the cached dirs' temp dirs; found by the container leak check,
fixed; `Main.cleanupAll` + engine `stop` releases remain the production
path). verify.sh step 7 measures the leak as a before/after diff around
clean binary runs so step 6's legitimately-live dirs cannot false-fail it.

## F. KNOWN ISSUES — signal/stop-path health (supervisor ground truth) + RSS

**TERM-stall (leaked processes).** Supervisor observed 4 leaked
`tail-tones -f` binaries (01:43/02:01 builds) alive 6 h later at 0.6–2.7 GB
RSS; THREE ignored SIGTERM entirely (ffplay-pipe, spawn, null+print-events —
the STALL SPANS ALL THREE BACKENDS ⇒ suspect is the SHARED stop path:
`ChildProcess.joinQuietly`-adjacent monitor waits / `Source.run` poll join /
self-pipe pump), only `kill -9` reaped them.
MY MEASUREMENTS: on the current macOS binary all three backends (`spawn`,
`ffplay-pipe`, `null`) plus media-spawn follow a static file and exit 0
within ~1–2 s of SIGTERM (scripted probe ×3 each, plus `MediaE2eSpec`
three-backend test with hard watchdog). **REPRODUCED in the devcontainer:** full-suite runs showed
`--backend ffplay-pipe` **ignoring SIGTERM entirely** (exited=false after the
15 s join budget; dt=15104 ms) under 500-test CPU load; a second run also hung
`null` (15.1 s) while `spawn` finished in 0.4 s — **the stall spans backends
under load**, exactly matching the supervisor's observation that ffplay-pipe,
spawn AND null(leaked) all ignored TERM. macOS host never stalls (<2 s,
measured 0.1–1 s with the same test). The stall is real under CPU pressure;
likely the mixer's final `sink.write` draining into a pipe whose `ffplay`
child is descheduled/starved, or a fade-window deadline × scheduling
interaction (null hanging points at the SHARED stop path — Source join /
self-pipe — over the mixer specifically). The `MediaE2eSpec`
three-backend test records the finding LOUDLY every run
(`[S12-term-finding] --backend X exited=.. dt=..ms` + a findings file) but
does not redden the suite for the hang itself — signal/stop-path health is
S13's defect to fix, not an S12-pinned contract. What S12 pins HARD:
`hardReap` proves every process is SIGKILL-reapable and ends TRULY GONE
(hang path ⇒ exit code must be exactly 137 = our kill; clean-TERM path ⇒ 0
or 128+sig), and no test may leak — the discipline that keeps the suite from
reproducing the 6-hour GB-RSS leakers. IF IT RECURS: `sample <pid>` of the
stalled process; suspects in order — (1) mixer thread blocked in `sink.write`
(child dead/descheduled), (2) `Source.run`/`FileTailer.follow` parked in
`Sleeper.system` `Thread.sleep` hit by EINTR/IMS monitor breakage (S0 spike D
family), (3) shutdown-hook chain stall. S13 (formal signals) owns this.

**RSS growth on static follow.** 15-minute probe (`-f --backend null -q` on a
file that stops changing, sampled every 3 min via `ps -o rss`):
23.6 → 41.2 → 41.5 → 69.7 → 77.1 MB ≈ **3.5 MB/min linear**. (spawn+media
with a 1 s mp3: flat 78.4 MB — the loop itself is not the leaker.) Extrapolates
to ~1.2 GB/6 h — matches the supervisor's 1.4→2.7 GB leakers EXACTLY, so the
grow-while-blocked symptom is this leak plus a stalled stop. Suspect: the
follow poll path allocating per-100 ms-poll garbage that immix retains (heap
growth without GC pressure returning pages, or a genuine retention in
`LineReader`/`FileTailer` buffers on no-change polls). NOT pinned to a line —
**S13 MUST** (owner of signals/stop-path health; repro script:
`-f --backend null -q static.log` + `ps -o rss` sampling; bisect by disabling
scheduler tick vs poll).
